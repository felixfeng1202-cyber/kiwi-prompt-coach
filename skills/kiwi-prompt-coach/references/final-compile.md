# 最终版编译清理

把草案视为“构建态”，把最终 Prompt 或 Skill 视为“运行态”。交付最终版前逐条审查角色、步骤、格式和约束，只让会改变目标 AI 实际行为或结果质量的内容进入运行态。

## 一、逐条分类

为每条要求在心里归类，不要把分类标签展示给用户：

- **运行规则**：目标 AI 在未来每次执行任务时都需要遵守。保留。
- **构建记录**：本轮共创中的解释、讨论结论、版本变化、修改理由、KIWI 操作步骤。删除。
- **重复规则**：已被更清晰的角色、步骤、成功标准或输出格式覆盖。合并或删除较弱的一条。
- **局部补丁**：为修正某个例子临时追加的“某场景不展示 / 不要做某事”。先判断是否可被更一般的正向规则吸收；可以就改写并合并，不能且确为长期业务要求才保留。
- **必要边界**：安全、合规、事实准确性、关键禁区、失败处理或用户明确要求的业务边界。即使是负向表述，也必须保留并尽量压缩。

## 二、四项清理

1. **删过程残留**：删除“根据刚才讨论”“这一版先……”“用户选择了……”“后续再补……”以及 KIWI 自己的提问、审查、归档和版本管理要求。
2. **去重复**：同一规则只保留一次；具体输出格式已经保证的事项，不再追加同义的“不要展示”。
3. **正向收束**：能用一个清晰的目标状态表达时，用“仅输出 X / 输出包含 A、B、C”替代多条“不要输出 Y、Z……”；不要为了正向化而弱化必要禁令。
4. **去偶发补丁**：仅为某个测试样例或本轮对话成立、对未来多数输入无作用的约束直接删除。若它揭示了稳定规律，把规律写进成功标准或输出契约，不保留原始补丁措辞。

Prompt 或 Skill 指令还要删除：不影响结果的泛化角色；无条件的“全面、深入、仔细思考”；并未修复真实失败的示例；对所有任务强制使用的工具；不属于明确交付要求的提供商专属格式、参数或版本补丁。保留可验证的成功标准、必要证据、行动权限和风险边界。

## 三、最小必要性测试

对每条仍准备保留的要求问：

> 删除这条后，在合理输入下，目标 AI 的行为、输出质量或风险边界会实质变化吗？

- **不会**：删除。
- **会，而且变化有害**：保留或与相邻规则合并。
- **无法判断**：如果可能改变用户意图，交付前只问这一处；不要擅自删除。

再做一次整体检查：最终产物中不得出现 KIWI、草案版本、共创过程、人工核验卡或“如何修改提示词”的元指令，除非目标任务本身就是提示词或 Skill 设计。

如果最终产物本身是 `SKILL.md`、系统提示词或其他指令文件，同样只保留该技能**运行时**需要执行的规则。开发过程中的测试说明、为什么这样改、仅为当前案例设置的展示/隐藏要求，不得因为它们曾出现在草案里就进入最终文件；只有会在未来调用中稳定改变正确行为的要求才保留。

## 四、典型转换

冗余草案：

> 输出一份三段式结论。不要展示分析过程。场景 A 也不需要展示推理。不要输出思考步骤。

若所有场景的真实要求相同，编译为：

> 仅输出三段式结论。

若“场景 A 不展示”只是本轮测试时的临时说明，直接删除；若它是区别于其他场景的长期业务规则，则用一条紧凑的条件规则保留。

## 五、交付行为

- 默认静默执行清理，不把逐条检查过程附在最终产物后。
- 只有清理会改变含义或存在冲突时，才在交付前向用户确认。
- 用户明确要求查看时，再简要说明删了哪些类别、合并了哪些规则；不要重新制造一份冗长过程记录。
