# 现代 Prompt 通用撰写规则

把 Prompt 写成跨模型可迁移的“最小充分任务合同”。不要机械加入角色、长步骤、示例、标签或推理口号。

## 一、撰写顺序

1. **先定义结果**：明确目标、交付物、成功标准和必要证据。先解决“怎样算完成”，再优化措辞。
2. **补足关键上下文**：只加入会改变判断的信息、变量和素材；必要时简要说明规则背后的原因，帮助模型正确泛化。
3. **明确输入与输出**：把指令、参考材料、变量输入和示例清楚分隔；写清输出必须包含什么、按什么顺序、如何取舍长度。
4. **定义行动边界**：区分回答、诊断、规划和实际执行；说明哪些安全操作可直接做，哪些外部、破坏性、高成本或扩范围动作必须确认。
5. **补充必要逻辑**：只有顺序、完整性、审批或可复现性重要时才规定步骤；模型可自行规划的部分只写目标、判断标准和边界。
6. **最后决定是否需要角色、工具和示例**：它们只有能带来可验证收益时才进入 Prompt。

## 二、核心规则

- **每条只写一次**：删除同义提醒、口号、泛化人格描述和已经由输出契约保证的限制。
- **清楚直接**：使用具体动词和可观察要求，不用“尽可能专业”“高质量完成”“深入思考”等无法验收的形容词。
- **结果优先于微观步骤**：说明要达到什么标准，避免替能力较强的模型规定每个思考动作。
- **正向描述优先**：用“仅输出 X”“内容包含 A/B/C”代替多条“不要输出……”。安全、合规和关键业务禁区保留为明确负向边界。
- **结构服从复杂度**：简单任务用自然段或短列表；混合长材料、变量和示例时使用一致的标题、围栏或语义标签，但不强制某种厂商专属格式。
- **工具策略具体**：只提供相关工具，并说明何时使用、处理什么、保留什么证据、何时停止或报告失败。不要写“充分利用所有工具”。
- **风格必须可观察**：不要只写“简洁、友好、专业”。应说明先给结论、需保留哪些事实与风险、是否需要确认问题、应删掉哪些低价值内容。
- **示例按价值加入**：示例只用于编码产品要求、稳定格式或修复已测得的失败；应贴近真实场景并覆盖必要差异。没有评测收益就省略。
- **要求证据与检查，不索要隐藏推理**：可要求定位依据、列出假设、引用来源、运行测试或交付前核对标准；不要要求展示完整思维链，也不要用“想得更久”替代明确标准。
- **长上下文先组织再提问**：将材料与问题清楚分开；多文档时保留来源或标识，需要事实依据时要求先定位相关片段再作答。
- **自主性与审批集中写一次**：不要在多个章节重复“先询问”“不要修改”，以免模型对安全、预期内的操作也频繁停顿。
- **用评测驱动迭代**：先确定代表性任务和判定标准；每次只改一组规则并复测。更短、更快或工具调用更少，只有结果仍通过验收时才算改进。

## 三、默认结构

按需选择并删除空章节，不要求每个 Prompt 都包含全部字段：

```markdown
## 目标
[要完成的结果]

## 上下文与输入
[会改变判断的背景、变量和素材]

## 交付与成功标准
[必须交付什么；怎样算正确；需要什么证据]

## 工作与权限边界
[仅在多步骤、工具或行动型任务中填写]

## 输出契约
[必须包含的内容、结构和长度取舍]

## 必要限制
[安全、合规和关键业务禁区]

## 示例
[只有示例能带来可验证收益时填写]
```

## 四、交付前自检

- 删除任一规则后，结果、质量或风险边界是否会实质变差？不会就删除。
- 是否存在重复、矛盾、无法验收或只服务当前案例的要求？
- 是否把建议和实际执行、允许操作和需确认操作分清？
- 是否明确了必须保留的内容，而不只是限制字数？
- 是否有至少一个代表性场景可以验证 Prompt？
- 是否包含提供商专属标签、参数或版本补丁？若有，删除；平台 API 配置应与通用 Prompt 分开交付。
